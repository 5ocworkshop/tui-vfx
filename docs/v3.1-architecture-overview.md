# v3.1 Architecture Overview

## Status

This is the durable overview for the clean-room `tui-vfx-contract` / `tui-vfx-next` kernel stack. It describes the contract stack being proven before recipe, runtime, studio, or migration work begins. It is not a legacy-compositor migration plan.

## Philosophy

v3.1 is a contract-first rendering model.

The goal is not to preserve the old implementation shape. The goal is to make every public semantic rule explicit, testable, documented, and discoverable by tools.

A render effect should not hide what it reads, writes, targets, emits, or mutates. Recipes, studio controls, validation, diagnostics, and runtime behavior should all flow from the same Rust-owned contract model.

The legacy engine is an oracle and inventory. It is not the source of truth for v3.1 semantics.

Short prompt form:

```text
Build the contract before porting effects. Every semantic fact needs one owner, one test, and one generated reference path.
```

## Reference path

```text
Serde
    owns JSON wire shape

Schemars
    generates JSON Schema from Rust types

Rustdoc comments
    become human-facing schema descriptions/reference text

Generated schema/reference docs
    become the public contract artifact
```

Rust contract types are the schema source of truth. Hand-written contract docs explain the system; they are not the authoritative machine-readable schema.

## Phase D0 boundaries

Phase D0 backfills schema/reference hygiene only. It does not change runtime behavior and does not add real effects, recipes, studio manifests, runtime bindings, phase graphs, trigger engines, descriptor expansion, or legacy migration.

## Phase D1 boundaries

Phase D1 adds only scene / element / layer composition semantics. It composes multiple local semantic surfaces into one final `Surface`; it does not add effect descriptors, recipe schemas, studio manifests, runtime bindings, phase graphs, trigger engines, legacy migration, template inheritance, a full layer graph, complex blending, or real effect ports.

## Phase D2 boundaries

Phase D2 is a design-document phase for template composition. It defines compile-time expansion rules for templates, mixins/traits, presets, profiles, and recipes. It does not implement template expansion, recipe schema/compiler code, runtime inheritance, descriptors, studio manifests, phase graphs, trigger engines, legacy migration, or real effect ports.


## Phase D3 boundaries

Phase D3 is a boundary and vocabulary phase. It classifies which current `tui-vfx-next` types are public contract vocabulary, proof implementation, schema roots, or test-only scaffolding. It adds a logical contract/proof/schema-root grouping in `tui-vfx-next` and documents the boundary in [`v3.1-contract-boundary.md`](v3.1-contract-boundary.md).

Phase D3 does not implement effect descriptors, recipe schemas, source authoring schemas, template expansion, runtime bindings, phase graphs, trigger engines, studio manifests, legacy migration, real effect ports, or complex blend/layer behavior.


## Phase E0 boundaries

Phase E0 makes the D3 logical boundary physical. `tui-vfx-contract` owns stable surface, scene, scope, write, sampler, diagnostic, id, and outcome DTOs plus stable schema generation. `tui-vfx-next` depends on `tui-vfx-contract` and keeps proof execution, toy stages/effects, proof-pipeline schemas, and semantic engine tests.

Phase E0 does not implement effect descriptors, recipe schemas, source authoring schemas, template expansion, runtime bindings, phase graphs, trigger engines, studio manifests, legacy migration, real effect ports, or complex blend/layer behavior.

## Phase E1 boundaries

Phase E1 adds a minimal schema-backed `EffectDescriptor` model to `tui-vfx-contract`. The descriptor declares identity, broad `EffectDomain`, `CellAccess`, `ScopeSupport`, `WriteSupport`, and `EffectLifecycle`. Validation checks can accept or reject requested scope kinds, role write policies, cell write policies, and write channels against those declared capabilities.

Phase E1 does not implement typed effect inputs.

## Phase F1 boundaries

Phase F1 adds the first typed input contract to `tui-vfx-contract`: a closed `ValueKind` vocabulary, tagged literal `Value`, `ValueSpec` defaults/ranges/enum domains, `EffectInputId`, `EffectInputSpec`, `RuntimeMutability`, bindable metadata, and `EffectDescriptor.inputs`. Descriptor input validation rejects type mismatches, invalid ranges, enum-domain errors, non-finite numbers, and invalid input ids.

Phase F1 does not implement `ValueSource`, parameters, signals, bindings, presets, recipe nodes, descriptor registries, runtime graphs, studio controls, legacy migration, real effect ports, or template expansion.

## Phase F2 boundaries

Phase F2 adds the declarative source layer to `tui-vfx-contract`: `ValueSource`, `ParameterId`, `ParameterSpec`, `SignalId`, `SignalSpec`, `BindingTarget`, `BindingMode`, and parameter-target `BindingSpec`. Validation can resolve parameter/signal references, check source/target kind compatibility, validate fallbacks, constrain numeric maps, and reject unknown parameter binding targets.

Phase F2 does not implement runtime parameter/signal stores, live override precedence execution, node graph identity, direct effect-input bindings, recipe schema/compiler, template expansion, studio manifests/controls, phase graphs, trigger engines, migration, or real effect ports.

## Phase G4 boundaries

Phase G4 adds the graph-local node I/O value bus. `EffectDescriptor.outputs` declares descriptor-local effect outputs, `NodeSpec.outputs` publishes graph values either from an effect output or by re-emitting a resolved node input, and `ValueSource::GraphValue` lets later node inputs consume a graph-local value. Graph values have a typed kind and an explicit shape, including `frameValue` and `cellField`, so scalar-producing nodes can model spatial scalar fields such as normalized-x samples without collapsing them into one global number.

`tui-vfx-next` proves sequence visibility, fan-out, input re-emission, parallel branch isolation, post-join visibility, child-order last-writer-wins value conflicts, error-on-conflict value policy, and field-driven dimming. G4 still does not implement runtime parameter/signal stores, F2 binding execution, direct node/effect-input binding targets, recipe source syntax/compiler, phases/triggers/dwell, visibility predicates, loopback signals, asset/procedural sources, studio manifests, legacy migration, or real effect ports.

## Phase H0 boundaries

Phase H0 adds stable source and asset contracts to `tui-vfx-contract`. A `SourceDescriptor` describes a surface producer rather than an effect over an existing surface. A `SourceSpec` instantiates that descriptor with typed inputs and structural asset refs. `SourceInputSpec` reuses the existing `ValueSpec`, `Value`, `ValueKind`, and `ValueSource` vocabulary so effect inputs, source inputs, parameters, signals, and graph values do not fork the value model.

`AssetSpec`, `AssetRequirement`, and `AssetRef` make assets explicit contract objects. Canonical asset refs are structured references by id, not string interpolation tokens such as `{{ flag_art }}`. H0 accounts for text, card, procedural, image, ANSI, command-capture, and asset-backed source needs from recipe examples without adopting current recipe field names as canonical schema. H0 still does not implement canonical recipe documents, recipe lowering/compiler, source-local pipeline syntax, real asset loading/resolution, real procedural rendering, runtime stores, phase/trigger/dwell engines, studio manifests, migration, or real source/effect ports.

## Phase H1 boundaries

Phase H1 adds the canonical recipe document root to `tui-vfx-contract`. `RecipeDocument` packages metadata, assets, source descriptors, source instances, the canonical graph, and recipe scenes into one strict post-authoring/lowering contract. `RecipeSceneElement` references a source instance that will produce the element surface, and `RecipeElementPipeline` provides an element-local graph/topology reference seam for future source-local pipeline integration.

H1 also adds [`VOCABULARY.md`](VOCABULARY.md) as the standing human contract vocabulary and `docs/new_kernel/H1_RECIPE_EVIDENCE_NOTES.md` as curated evidence that representative legacy recipes map by concept rather than by field name. H1 still does not implement template expansion, legacy migration, runtime stores, binding execution, phase/trigger/dwell engines, studio manifests, asset loading, procedural rendering, or real source/effect ports.
