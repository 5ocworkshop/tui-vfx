# Packet 1.1.A — Bundle Filter / Mask / Sampler spatial-context parameters

> **STATUS: QUEUED, NOT EXECUTABLE TODAY.** This packet is **blocked** on
> Slice 6.6 (`TextTransformer` migration to `TransformContext`) landing
> first. The plan for that work lives at
> `docs/design/tui-vfx-transform-context-implementation-plan.md` (v1.0.0).
> Once Slice 6.6 is green on master, this packet becomes the next slice.

> **For the assignee.** Read the must-read docs in §8 *and* the completed
> Slice 6.6 source code before executing. The TransformContext migration is
> the canonical exemplar for what you are about to do at three times the
> scale; the patterns it leaves behind on disk are part of the spec.

## 1. Task

Define `VfxCellContext` in `tui-vfx-types` (the lowest-common crate that
already owns `Cell`) carrying the eight spatial-context fields shared
across `Filter`, `Mask`, `Sampler`, and `StyleShader`. Migrate the three
unbundled traits in `tui-vfx-compositor/src/traits/` to take a single
`&VfxCellContext` parameter. Refactor `ShaderContext` (in `tui-vfx-style`)
to compose `VfxCellContext` rather than duplicate the eight fields. Per
sweep §6.1 Option C: this is the only home that satisfies Intentions 1
(grid-first compositor independence), 8 (Vfx prefix on contract-producing
wire-format types), and 26 (SSOT — shared semantics live once).

## 2. Why this matters

Three sibling traits already absorbed two breaking signature churns each
(metadata records BREAKING CHANGE on `Filter` v3.0.0, `Sampler` v2.0.0,
`Mask` similar). The next addition — runtime parameters / role-map /
phase awareness for binding-driven filters — is queued. Without bundling,
each trait's ~30+ impls re-pay the same churn for every new field.

The Slice 6.6 TransformContext work establishes this pattern on *one*
trait (`TextTransformer`). This packet generalizes that pattern to the
three siblings with the largest impl sets in the repo. Sweep estimate: ~56
impl files across the three traits, plus pipeline dispatch and tests.
Migration is mechanical (replace tuple-of-params with `&ctx`); the work
is throughput, not architecture, *because the architecture is already
decided* — see §6.1 of the sweep.

## 3. Success condition

- `VfxCellContext` defined in `crates/tui-vfx-types/src/cls_vfx_cell_context.rs`
  with the eight shared fields: `local_x: u16`, `local_y: u16`, `width:
  u16`, `height: u16`, `screen_x: u16`, `screen_y: u16`, `t: f64`, `phase:
  AnimationPhase` (or whichever phase enum already lives at the lowest
  appropriate crate — confirm at slice-start; if `AnimationPhase` is in
  `tui-vfx-style`, hoist it down to `tui-vfx-types` as part of this
  packet).
- `Filter::apply` signature becomes `fn apply(&self, cell: &mut Cell, ctx:
  &VfxCellContext)` — replacing the current `(cell, x, y, width, height,
  t)` positional tuple at
  `crates/tui-vfx-compositor/src/traits/filter.rs:93`.
- `Mask::is_visible` signature becomes `fn is_visible(&self, ctx:
  &VfxCellContext) -> bool` — replacing `(x, y, w, h, progress)` at
  `crates/tui-vfx-compositor/src/traits/mask.rs:7`. The `progress`
  parameter today is the same `f64` clock as `t`; confirm during
  migration whether the rename matters or whether `Mask` should keep a
  `progress` accessor on `VfxCellContext` for clarity.
- `Sampler::sample` signature becomes `fn sample(&self, ctx:
  &VfxCellContext) -> Option<(u16, u16)>` — replacing `(dest_x, dest_y,
  width, height, t)` at `crates/tui-vfx-compositor/src/traits/sampler.rs:26`.
- `ShaderContext` in `crates/tui-vfx-style/src/traits/cls_shader_context.rs`
  refactored to compose: `pub struct ShaderContext { pub cell:
  VfxCellContext, pub runtime_params: Arc<ShaderRuntimeParams>, pub roles:
  Arc<RoleMap> }`. Decide at slice-start whether to add a `Deref<Target =
  VfxCellContext>` impl for backward-compatible `ctx.local_x` field
  access (sweep §6.1 open follow-on).
- All ~56 trait impls (31 filters + 13 masks + 12 samplers per sweep
  count) updated to take `&VfxCellContext` and access fields by name.
  Most impls will read fewer fields than they currently take as
  positional args — most can ignore the bundle entirely with `_ctx`.
- Pipeline dispatch sites in `tui-vfx-compositor` construct
  `VfxCellContext` once and pass `&ctx` to all three trait surfaces.
- Tests updated. Most pipeline tests construct positional arguments by
  hand today; they will need to construct a `VfxCellContext` literal
  instead. Provide a `VfxCellContext::test_default()` helper for the
  zero-fill case.
- All workspace tests green: `cargo test --workspace` from
  `/usr/projects/tui-vfx`.
- gt-design downstream is unblocked. If gt-design has Filter / Mask /
  Sampler impls (likely yes), surface that as a coordinated migration in
  the report — that is the cross-repo audit per Intention 41.

## 6. Write scope (smallest justified set)

Migration order matters — do NOT do all three traits in parallel:

1. **Define `VfxCellContext`** at
   `crates/tui-vfx-types/src/cls_vfx_cell_context.rs`. Add to
   `tui-vfx-types/src/lib.rs` exports. Inline tests for the
   constructor and field access. Land this commit first.

2. **Refactor `ShaderContext`** to compose `VfxCellContext`. If a `Deref`
   impl is added, the pre-existing `ctx.local_x` accesses keep
   compiling; if not, every `style_at` impl in `tui-vfx-style` and
   `gt-design` updates to `ctx.cell.local_x`. Decide at slice-start;
   document the choice in the commit message. Land this as commit 2.

3. **Migrate `Mask` first** — smallest impl set (13 files), no historical
   churn, lowest risk for the canonical pattern. Land as commit 3.

4. **Migrate `Sampler` second** — already at v2.0.0; this bumps to
   v3.0.0. ~12 impls. Land as commit 4.

5. **Migrate `Filter` last** — largest impl set (31 files), gate on
   commits 3 + 4 passing CI. ~31 impls. Land as commit 5.

6. **Cross-repo audit (Intention 41)** — gt-design and any other
   downstream consumer with Filter / Mask / Sampler impls. Coordinate
   the migration across repos. Land as commit 6 (or as separate commits
   per repo).

### Out of scope

- Do NOT bundle in Finding 1.1.B (`Bindable*::evaluate` signature
  unification). That is "wait for third trigger" per the sweep.
- Do NOT bundle in Finding 1.6.A (`cls_filter_spec.rs` split-up). That
  is its own slice in V3 cross-family work.
- Do NOT add `runtime_params: Arc<ShaderRuntimeParams>` or `roles:
  Arc<RoleMap>` to `VfxCellContext`. Those live on `ShaderContext` only;
  per sweep §6.1, the compositor does not import style semantics.
  Filter / Mask / Sampler do not get runtime-params access from this
  packet; that is queued for after Finding 1.2.A (`Bindable<T>`
  consolidation) gives the family a binding context.
- Do NOT change the `Cell` type itself.

## 7. Repo-boundary guardrails

- The lowest-common crate ruling (sweep §6.1 Option C) is `tui-vfx-types`.
  Do not put `VfxCellContext` in `tui-vfx-style` (would force
  compositor to depend on style — Intention 1 violation) or in
  `tui-vfx-compositor` (would split the SSOT — Intention 26 violation).
- The `Vfx` prefix is mandatory: per Intention 8, this is wire-relevant
  contract-producing data crossing crate boundaries through every
  Filter / Mask / Sampler impl.
- Cross-repo migration must respect Intention 41: audit the four-repo
  scope (`tui-vfx`, `tui-vfx-recipes`, `mixed-signals`, `gt-design`)
  before declaring done.
