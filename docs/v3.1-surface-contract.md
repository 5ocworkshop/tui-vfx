# v3.1 Surface Contract — Clean-Room Contract Through Phase E1

## Status

Phase A defined the clean-room semantic surface rules proven by `tui-vfx-next`. Phase B extends that proof with non-identity sampled-source semantics. Phase C adds ordered multi-stage pipeline semantics. Phase D0 adds schema/reference readiness. Phase D1 adds scene / element / layer composition semantics for multiple placed semantic surfaces. Phase D2 defines authoring-time template composition above runtime. Phase D3 classifies the contract/proof boundary. Phase E0 moves stable contract DTOs and stable schemas into `tui-vfx-contract`. Phase E1 adds the minimal effect descriptor capability contract. This document is not a migration plan for the legacy compositor.

## Philosophy

v3.1 is a contract-first rendering model. Build the contract before porting effects. Every semantic fact needs one owner, one test, and one generated reference path. The legacy engine is an oracle and inventory, not the source of truth for v3.1 semantics. See [`v3.1-architecture-overview.md`](v3.1-architecture-overview.md).

## Goals

- Define a grid-first, ecosystem-agnostic surface model.
- Make cells, roles, scope evaluation, sampling, writes, and diagnostics explicit.
- Prove role preservation, sampled-source role scopes, destination-local geometry scopes, skipped-cell behavior, transparent empty writes, zero-cell diagnostics, explicit procedural role writes, non-identity sampling, ordered multi-stage pipeline behavior, and multi-element scene composition with tests.
- Classify which current names are stable v3.1 contract vocabulary and which are proof-only implementation artifacts.

## Non-goals

Phase A/B/C/D0/D1/D2/D3/E0/E1 does not build or replace:

- recipe compiler or recipe schema
- runtime, studio, trigger engine, phase graph, or demo player
- legacy compositor, style, content, or shadow internals
- real visual effects such as CRT, typewriter, matrix rain, or shadows
- migration aliases or deprecated v1/v2 names
- descriptor registries or full input/value/source descriptor systems
- source authoring schemas or template expansion implementation

## Surface

A `Surface` is a rectangular cell grid plus one semantic role channel for every surface position. It is destination-sized and row-major. It has optional `SurfaceMetadata` for producer/layer labels, but metadata is not used for rendering semantics in Phase A/B/C.

The surface is grid-first. It does not mention ratatui, crossterm, terminal escape codes, widgets, recipes, or studio UI.

## Cell channels

A surface cell position has visual cell channels and one semantic role channel.

Visual cell channels:

- glyph
- foreground color
- background color
- modifiers
- modifier alpha

Semantic channel:

- role

The role is a surface semantic channel, not a field on `tui_vfx_types::Cell`. Role updates are governed by role write policy.

## Empty, transparent, skipped, and unfilled cells

- **Empty cell**: a space glyph with transparent foreground and transparent background, matching `Cell::is_empty()`.
- **Transparent cell**: a cell whose color channels are transparent. In Phase A/B/C, the empty transparent cell is the important tested case.
- **Skipped cell**: no write occurs. Destination cell channels and destination role remain unchanged.
- **Unfilled cell**: a destination cell that has not been reached by a writer in the current operation. It behaves like a skipped cell for that operation.

Writing an empty transparent cell is not the same as skipping. The default write policy writes it and can clear destination content. `SkipTransparentEmpty` is an explicit policy that preserves destination cell and role when the source write is empty.

## Role model

Every surface position has exactly one `RoleTag`.

First-class built-in roles are the roles defined by `tui-vfx-types`:

- `Background`
- `Text`
- `Title`
- `Caption`
- `Border`
- `Image`
- `Icon`
- `Indicator`
- `Highlight`
- `Shadow`
- `Decoration`
- `Procedural`

Custom roles:

- `Custom(name)`

Custom roles are allowed through `RoleTag::Custom`. They are part of the role model, but they are not built-in roles. Phase A/B/C/D0/D1/E0/E1 does not add aliases, shorthand names, or legacy compatibility names in `tui-vfx-contract` or `tui-vfx-next`.

## Sampling model

Source-to-destination operations evaluate each destination-local coordinate through a `CoordinateSampler`:

```text
destination coordinate
    -> sampler
    -> sampled source coordinate
    -> sampled source cell
    -> sampled source role
    -> scope evaluation
    -> write policy
    -> destination cell + destination role
```

`IdentitySampler` maps destination `(x, y)` to source `(x, y)` and preserves Phase A behavior.

`ShiftSampler { dx, dy }` maps destination `(x, y)` to source `(x + dx, y + dy)`. Positive `dx` samples from the source cell to the right of the destination. Positive `dy` samples from the source cell below the destination. Shifted coordinates outside the source surface return no sample.

A destination coordinate with no in-bounds source sample is skipped. The destination cell and destination role are preserved.

## Scope model

Phase A/B/C/D0/D1 supports this small `ScopeSpec` set:

- `All`
- `Role(RoleTag)`
- `Rect(Rect)`
- `RowRange { start, end }`
- `ColumnRange { start, end }`

`ScopeEvalInput` carries destination coordinates, sampled-source coordinates, sampled-source role, and destination role. Scope evaluation is explicit about both coordinate and role spaces.

## Coordinate spaces

Geometry scopes use `CoordinateSpace::DestinationLocal` by default. With non-identity sampling, a destination-local rectangle, row range, or column range matches the destination coordinate even when that destination samples a different source coordinate.

`CoordinateSpace::SampledSource` is available for operations that intentionally want geometry scopes to select by sampled-source coordinates.

## Role spaces

Role scopes use `RoleSpace::SampledSource` by default. That means `ScopeSpec::Role { role: RoleTag::Text }` selects destination cells whose sampled source role is `Text`, even when the destination role before writing is something else and even when the sampled source coordinate differs from the destination coordinate.

`RoleSpace::Destination` is available when a role scope should select by the pre-write destination role. Phase B proves that destination role space can behave differently from sampled-source role space under a shifted sampler.

## Write policies

Cell write policy:

- `WriteCell`: write cell visual channels exactly, including empty transparent cells.
- `SkipTransparentEmpty`: skip writes whose cell is empty and transparent; preserve destination cell and role.

Role write policy:

- `PreserveDestination`: leave the destination role unchanged.
- `CopySampledSource`: copy the sampled-source role to the destination.
- `SetExplicit { role }`: set a specified role such as `Shadow` or `Procedural`.

A visual-only effect preserves the role already present on the destination surface by using `PreserveDestination`.

A source-to-destination copy or transform writes the sampled source role first by using `CopySampledSource`. Later visual-only effects over that materialized destination preserve that role.

A procedural writer may use `SetExplicit`.

## Zero-cell scope behavior

If a scope matches zero sampled write candidates, the operation emits a structured `SurfaceDiagnostic` with `SurfaceDiagnosticCode::ZeroCellScope` and does not mutate the destination.

Phase B computes zero-cell diagnostics from the same sampled-source path used by actual writes. Out-of-bounds samples are skipped before scope matching. Role scopes inspect the sampled source role from the sampled coordinate unless `RoleSpace::Destination` is explicitly selected.

## Diagnostic behavior

Diagnostics are structured:

- level
- stable code
- message
- optional path
- optional hint

Phase A/B/C defines zero-cell scope and surface-size mismatch diagnostics. Diagnostics are not plain strings.

## Shadow and procedural role writes

Phase A/B/C/D0/D1 does not implement real shadow rendering. It only proves that a procedural writer can explicitly write a role such as `RoleTag::Shadow` by using `RoleWritePolicy::SetExplicit { role: RoleTag::Shadow }`.

That rule is the surface contract needed by later shadow/procedural work: generated cells may intentionally mark their semantic role instead of inheriting a sampled-source role.

## Phase C ordered pipeline semantics

Phase C defines a tiny ordered pipeline abstraction for `tui-vfx-next`. A `SurfacePipeline` owns an ordered list of `PipelineStage` values. The pipeline starts with the initial surface as the current surface.

For each stage:

1. The stage read surface is the current surface.
2. The stage write surface is a fresh next surface initialized as a clone of the current surface.
3. The stage applies its copy/sample, visual-only, explicit-role, or test-helper toy semantics from read to next.
4. After the stage completes, next becomes the current surface for the following stage.

This means later stages see earlier stage cell writes and role writes. Stage order is semantic: reordering stages may change the final surface.

A skipped cell in a later stage preserves that stage's current destination surface, not the original input surface. Because each next surface starts as a clone of current, out-of-bounds samples, zero matches, and explicit skip policies keep prior stage output intact.

Within a pipeline stage, `sampled source role` means the role at the sampled coordinate of that stage's read surface. It does not necessarily refer to the original input surface. Non-identity samplers therefore preserve the Phase B sampled-source role rules while operating on current stage data.

Pipeline diagnostics are emitted in stage order. Diagnostics from a stage carry stable stage identity in their message and `path`, using `pipeline.stage[index].name`, so zero-cell scope diagnostics can be traced back to the stage that produced them.

Phase C deliberately keeps stages tiny: copy/sample, dim visual-only, explicit role writer, and a small glyph-rewrite test helper. It does not add real effects, descriptor registry/model expansion, recipes, a runtime graph, or trigger semantics. The old tiny proof descriptor is retired in Phase E1; durable descriptor vocabulary lives in `tui-vfx-contract`.

## Phase D1 scene / element / layer composition semantics

Phase D1 defines a minimal scene model above `Surface`. A `Scene` has a final width and height and a declaration-ordered list of `SceneElement` values. Each element owns an element-local `Surface`, a stable `ElementId`, an optional `LayerId`, a signed `ElementPlacement`, a `z_index`, a `ClipPolicy`, and cell/role write policies.

Element identity is not role identity. A scene element may be named `titleCard` while the cells it writes carry `RoleTag::Text`, `RoleTag::Border`, or any other semantic role. Future recipe and diagnostic systems should use element ids for instance identity and roles for semantic cell classification.

Composition order is deterministic:

1. Elements compose by ascending `z_index`.
2. Elements with the same `z_index` compose by declaration order.
3. Later-composed written cells overwrite earlier/current cells and roles according to role write policy.

Element placement maps element-local coordinates into scene coordinates:

```text
element local (x, y)
    + placement (scene x, scene y)
    -> final scene coordinate
```

Signed placement allows partially offscreen elements. Out-of-bounds local cells are clipped. `ClipPolicy::Clip` clips silently; `ClipPolicy::Warn` clips and emits one element-aware diagnostic with a `scene.element[index].id` path.

Scene write semantics reuse the existing surface write distinction:

- `CellWritePolicy::WriteCell` writes empty transparent cells and can clear lower/current content.
- `CellWritePolicy::SkipTransparentEmpty` skips empty transparent cells and preserves the lower/current cell and role.
- `RoleWritePolicy::CopySampledSource` copies the element-local role to the final scene.
- `RoleWritePolicy::PreserveDestination` preserves the lower/current role.
- `RoleWritePolicy::SetExplicit { role }` writes an explicit role.

Scene diagnostics are structured `SurfaceDiagnostic` values. D1 adds `SurfaceDiagnosticCode::SceneElementClipped` for clipped elements when warning is requested. Diagnostic order follows deterministic composition order.

Phase D1 deliberately keeps layers lightweight. `LayerId` is an optional grouping identity on `SceneElement`; there is no full layer graph, layer blending model, or layer-scoped execution engine yet.



## Phase D3 contract / engine boundary

Phase D3 adds no new rendering semantics. It classifies the current clean-room crate so later descriptor and recipe work can depend on stable vocabulary without inheriting toy proof shapes. See [`v3.1-contract-boundary.md`](v3.1-contract-boundary.md).

Stable contract vocabulary includes:

- `Surface`, `SurfaceMetadata`, and `CellChannel`
- `ScopeSpec`, `CoordinateSpace`, and `RoleSpace`
- `CellWrite`, `CellWritePolicy`, and `RoleWritePolicy`
- `CoordinateSampler`, `PipelineSampler`, and `ShiftSampler` semantics
- `SurfaceDiagnostic`, `SurfaceDiagnosticCode`, and `DiagnosticLevel`
- `Scene`, `SceneElement`, `SceneOutcome`, `ElementId`, `LayerId`, `ElementPlacement`, and `ClipPolicy`
- operation outcomes such as `ApplyOutcome`, `PipelineOutcome`, and `SceneOutcome`

Proof-facing implementation includes:

- `SurfaceEngine` and the low-level apply/scope helper functions
- `SurfacePipeline` as a checked proof pipeline root
- `PipelineStage` as a toy proof enum, not the future descriptor model
- `DimEffect` and `ExplicitRoleWriteEffect` as proof artifacts

`ScopeSpec` is the current canonical generalized scope vocabulary. Coordinate and role spaces remain operation-level context rather than fields embedded inside scope values. Pipeline and scene composition reuse the same cell/role write policies. Diagnostics keep stable codes plus path strings for D3; structured identity fields are deferred until recipe schemas require them.

## Phase E1 minimal effect descriptor model

Phase E1 defines what an effect is allowed to do, not how all inputs are configured. `EffectDescriptor` lives in `tui-vfx-contract` and declares:

- stable `EffectId`, version, display name, and optional category metadata
- `EffectDomain` such as `contentGenerator`, `frameFilter`, `coordinateSampler`, or `shadow`
- `CellAccess` read and write channels
- `ScopeSupport` for supported `ScopeSpec` kinds and scope spaces
- `WriteSupport` for supported cell and role write policies
- `EffectLifecycle` completion/reset/seek/determinism metadata

Descriptor validation can reject unsupported scope kinds, unsupported write policies, and attempted writes to undeclared cell channels. This is intentionally smaller than a registry or runtime graph. Effect input contracts are intentionally deferred to Phase F: no `ValueKind`, `ValueSource`, defaults, ranges, runtime mutability, parameters, signals, or bindings are added in E1.

## Schema/reference readiness

Phase D0 makes the existing Phase A/B/C public contract-visible types schema-reference ready. For v3.1 clean-room contracts:

- Serde owns the JSON wire shape.
- Schemars generates JSON Schema from Rust types.
- Rustdoc comments become human-facing schema descriptions/reference text.
- Generated schemas in `schemas/v3.1/contract/` are the stable machine-readable public contract artifacts. `schemas/v3.1/next/` now holds proof-pipeline artifacts only.

A public v3.1 contract-visible type is schema-reference ready when it derives or intentionally implements `Serialize`, `Deserialize`, and `JsonSchema`; uses a strict Serde shape where JSON-facing; has rustdoc on public types, fields, enum variants, and non-obvious defaults/policies; and appears in generated schema output or is explicitly marked internal.

The checked schema roots are:

- `schemas/v3.1/contract/surface.schema.json` — `Surface`
- `schemas/v3.1/contract/scope.schema.json` — `ScopeSpec`
- `schemas/v3.1/contract/write.schema.json` — `CellWrite`
- `schemas/v3.1/contract/diagnostic.schema.json` — `SurfaceDiagnostic`
- `schemas/v3.1/contract/scene.schema.json` — `Scene`
- `schemas/v3.1/contract/element.schema.json` — `SceneElement`
- `schemas/v3.1/contract/outcome.schema.json` — `SceneOutcome`
- `schemas/v3.1/contract/effect-descriptor.schema.json` — `EffectDescriptor`
- `schemas/v3.1/next/sampler.schema.json` — `PipelineSampler` proof artifact
- `schemas/v3.1/next/pipeline.schema.json` — `SurfacePipeline` proof artifact

Runtime helpers such as `SurfaceEngine`, scope-coordinate helpers, diagnostic annotation helpers, and glyph rewrite helpers are intentionally not schema roots. `CoordinateSampler` is the behavioral sampler contract, but trait/function shapes are not schema roots. `SurfacePipeline` and `PipelineSampler` remain checked proof-pipeline roots; `PipelineStage` must not be treated as the effect descriptor model. The durable `EffectDescriptor` root is capability-only in Phase E1.

## Phase A/B/C/D0/D1/D2/D3/E0/E1 boundaries

`tui-vfx-contract` may depend on `tui-vfx-types`, `serde`, and `schemars`. It must not depend on `tui-vfx-next`, `tui-vfx-compositor`, `tui-vfx-style`, `tui-vfx-content`, or `tui-vfx-shadow`. `tui-vfx-next` depends on `tui-vfx-contract` and keeps proof execution, toy stages, and proof schemas.
