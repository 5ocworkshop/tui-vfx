# v3.1 Template Composition Design

## Status

This is the Phase D2 design document for v3.1 template composition. It is intentionally a design artifact, not an implementation. It defines how reusable authoring structure should expand into a strict canonical v3.1 recipe before validation, compilation, and runtime.

## Philosophy

Template composition is an authoring-layer feature. It must not leak into the runtime surface, pipeline, or scene engines.

The runtime should never ask:

```text
Did this element come from a template?
Which parent template supplied this node?
Which mixin added this parameter?
```

Those questions belong to expansion diagnostics and editor tooling. Runtime receives a canonical recipe whose scene, elements, nodes, phases, scopes, values, and policies are concrete.

The core rule is:

```text
templates / mixins / presets / profiles / recipes
        ↓
deterministic expansion with provenance
        ↓
strict canonical v3.1 recipe
        ↓
validation
        ↓
compiler/runtime
```

Use compile-time composition, not runtime inheritance.

## Non-goals

Phase D2 does not implement:

- template expansion code;
- recipe schema/compiler;
- runtime inheritance;
- effect descriptor expansion;
- studio manifest;
- runtime bindings;
- phase graph or trigger engine;
- legacy migration;
- legacy aliases;
- real effect ports.

It also does not introduce public Rust contract types. If a later phase adds Rust DTOs for these concepts, the D0 schema/reference rule applies.

## Concept vocabulary

### Template

A template defines reusable structure. It may declare parameters, slots, scene elements, node/stage skeletons, defaults, and sealed fields.

Templates answer:

```text
What reusable structure exists?
Where may a recipe fill content?
Which policies are fixed?
Which defaults can be overridden?
```

A template may define:

- scene element skeletons;
- node/stage skeletons;
- slots;
- parameter declarations;
- default values;
- default scopes;
- default write policies;
- sealed/final fields;
- provenance labels for diagnostics.

A template should not depend on runtime state and should not execute.

### Mixin / trait

A mixin or trait is an additive reusable fragment. It should not create an open-ended parent hierarchy.

Mixins answer:

```text
What extra reusable capability can be added to a template or recipe?
```

Examples:

- add a cursor element;
- add a shadow element skeleton;
- add diagnostics metadata;
- add a common timing parameter group;
- add a standard focus/highlight stage skeleton.

Mixins are ordered when multiple are used. Their merge behavior is deterministic. A mixin conflict is an error unless the consuming recipe declares an explicit override.

### Preset

A preset is values-only.

Presets answer:

```text
Which parameter values should be used for this existing structure?
```

A preset may set or override values such as colors, durations, strengths, easing choices, density, or default timing. It must not add structure: no new elements, nodes, slots, scopes, or phases.

If a reusable unit adds structure, it is a template or mixin, not a preset.

### Profile

A profile is an environment or product-mode value bundle. It selects values for a known recipe/template surface without changing structure.

Examples:

- `highContrast`;
- `lowMotion`;
- `denseTerminal`;
- `demoMode`;
- `batterySaver`.

Profiles are values-only like presets, but profiles are selected for execution context rather than design flavor. A profile may be layered after presets using the same explicit override rules.

### Recipe

A recipe is the author-facing document that chooses templates/mixins/presets/profiles, fills slots, adds concrete structure, and declares overrides.

A source recipe may contain template references before expansion. A canonical recipe may not.

### Canonical v3.1 recipe

The canonical recipe is the strict expanded output. It contains no template, inheritance, alias, preset, profile, or mixin references.

It is the only shape that validation, compilation, and runtime should consume.

## Expansion pipeline

```text
+==================================================================================================+
|                          v3.1 TEMPLATE COMPOSITION PIPELINE                                      |
+==================================================================================================+

        +-------------------------------+
        | Source Recipe                 |
        |                               |
        |  uses templates               |
        |  applies mixins               |
        |  selects presets/profiles     |
        |  fills slots                  |
        |  declares overrides           |
        +---------------+---------------+
                        |
                        v
        +-------------------------------+
        | Load Composition Inputs       |
        |                               |
        |  templates                    |
        |  mixins / traits              |
        |  presets                      |
        |  profiles                     |
        +---------------+---------------+
                        |
                        v
        +-------------------------------+
        | Expand Structure              |
        |                               |
        |  instantiate templates        |
        |  apply ordered mixins         |
        |  fill slots                   |
        |  namespace ids                |
        +---------------+---------------+
                        |
                        v
        +-------------------------------+
        | Apply Values                  |
        |                               |
        |  template defaults            |
        |  presets                      |
        |  profiles                     |
        |  recipe overrides             |
        +---------------+---------------+
                        |
                        v
        +-------------------------------+
        | Validate Composition          |
        |                               |

        |  provenance coverage          |
        +---------------+---------------+
                        |
                        v
        +-------------------------------+
        | Canonical v3.1 Recipe         |
        |                               |

        +---------------+---------------+

        +-------------------------------+

```

Expansion must be deterministic. Given the same input documents and versions, the canonical recipe and diagnostics must be byte-stable except for non-semantic formatting choices defined by tooling.

## Merge model

### Maps

Maps merge by key.

Default behavior:

```text
same key from one source       -> accepted
same key from multiple sources -> conflict unless explicit override
```

Explicit override syntax is required when a later source intentionally replaces an earlier value.

Recommended precedence order for value application:

```text
template defaults
    < preset values
    < profile values
    < recipe explicit overrides
```

Higher precedence still needs explicit override syntax when replacing a non-default or sealed-sensitive field.

### Arrays

Arrays do not merge implicitly.

Default behavior:

```text
array supplied by child without operation -> replace only where replacement is allowed
append/prepend/insert/remove              -> explicit operation required
```

Recommended initial operations:

- `replace` for whole-array replacement where allowed;
- `append` for additive lists where ordering is non-ambiguous;
- `insertBefore` / `insertAfter` only when stable ids exist;
- no `remove` in the first implementation phase.

Implicit array append is forbidden because it hides ordering changes.

### Scalars

Scalars replace only through allowed override paths. A scalar conflict without an explicit override is an error.

### Null / unset

`null` should not mean remove unless a field explicitly defines nullable semantics. Removal needs an explicit operation in a later implementation phase.

## Override rules

Overrides must declare intent.

Recommended shape for future schema design:

```text
overrides:
  parameters.speed:
    op: replace
    value: 1.25
    reason: "Recipe wants a faster card entrance."
```

The exact wire shape is deferred to the recipe schema phase, but the semantic requirement is locked here:

```text
No accidental override.
No silent key collision.
No inherited safety-policy replacement without explicit authorization.
```

An override record should identify:

- target path;
- operation;
- new value or fragment;
- expected prior owner when useful;
- reason or source note for human review;
- whether sealed/final policy allows it.

## Sealed and final fields

Templates may mark fields as sealed/final.

Sealed fields protect safety or semantic identity. Examples:

- element ids required by diagnostics;
- role-write policy for a semantic element;
- scope boundaries for a safety-critical mask;
- phase transition rules;
- accessibility / reduced-motion compliance settings;
- provenance labels.

Initial recommendation:

```text
sealed fields cannot be overridden by recipes, presets, profiles, or mixins.
```

If future product needs require exceptions, they should use an explicit privileged override mode with diagnostics and policy review. Do not design that exception into the default path.

## Id namespacing

Ids must be deterministic and collision-resistant.

D2 locks the requirement, not the final syntax. A future schema phase should choose exact separators and escaping rules.

Recommended model:

```text
template instance id + local id -> canonical id
```

Examples:

```text
card.template:title      -> card.title
modal.template:backdrop  -> modal.backdrop
focusMixin:ring          -> loginButton.focusRing
```

Rules:

- Template-local ids are scoped to the template instance.
- Slot-filled ids are scoped to the slot owner unless the slot contract says otherwise.
- Mixins must declare whether their ids are local to the receiving element/template or global.
- Global ids require explicit declaration.
- Any collision after namespacing is an error unless an explicit override operation targets that id.

Element ids remain instance identities. They must not be encoded as roles.

## Slot filling

Slots are named extension points in templates.

A slot contract should define:

- accepted content kind;
- cardinality;
- default content, if any;
- whether the slot is required;
- allowed id namespace for filled content;
- allowed override operations;
- whether filled content may introduce parameters or nodes;
- provenance path used for diagnostics.

Recommended slot kinds:

```text
element
node
stage
parameter
value
scope
phase
fragment
```

Slot cardinality:

```text
one
zeroOrOne
many
```

A missing required slot is a structured diagnostic. Extra content in a single-cardinality slot is a structured diagnostic. Slot fill order is declaration order unless an explicit ordering operation is used.

## Conflict diagnostics

Conflicts must be structured. D2 does not add Rust diagnostic types, but it locks the future diagnostic categories.

Recommended conflict categories:

```text
TemplateInputNotFound
TemplateVersionMismatch
RequiredSlotMissing
SlotCardinalityExceeded
IdCollision
ImplicitOverrideConflict
SealedFieldOverride
UnsupportedArrayOperation
PresetAddsStructure
ProfileAddsStructure
AmbiguousMixinOrder
TemplateCycle
CanonicalRecipeContainsTemplateReference
```

Each diagnostic should report:

- severity;
- stable machine-readable code;
- human-facing message;
- source path in the template/preset/profile/recipe;
- expanded canonical path when available;
- conflicting owners;
- remediation hint.

## Provenance model

Expansion must preserve provenance for diagnostics and tooling even though canonical runtime recipes contain no template references.

Distinguish two outputs:

```text
Canonical recipe:
    strict runtime/compiler input, no template refs.

Expansion report:
    tooling/debug artifact with provenance map and diagnostics.
```

A provenance entry should connect:

```text
canonical path
    -> source document id
    -> source path
    -> source kind (template/mixin/preset/profile/recipe)
    -> operation (define/default/fill/override/append/etc.)
```

Diagnostics should be able to say both:

```text
expanded recipe path: scene.elements[3].placement.x
template source path: templates.card.slots.title.placement.x
```

Runtime does not need the full provenance map. Tooling, compiler diagnostics, and studio/editor inspection do.

## Canonical expanded recipe output

A canonical v3.1 recipe should contain only concrete contract concepts.

Illustrative shape:

```text
recipe:
  metadata:
    id: login.modal
    version: 3.1
  scene:
    width: 80
    height: 24
    elements:
      - id: modal.backdrop
        layer: background
        placement: { x: 0, y: 0 }
        zIndex: 0
        surfaceSource: ...
      - id: modal.card
        layer: foreground
        placement: { x: 20, y: 6 }
        zIndex: 10
        surfaceSource: ...
  graph:
    nodes:
      - id: modal.card.enter
        effect: ...
        scope: ...
        writePolicy: ...
  parameters:
    durationMs: 240
    accentColor: ...
```

The exact recipe schema is not locked in D2. The rule is locked:

```text
No template refs remain.
No aliases remain.
No implicit inheritance remains.
Every id is concrete.
Every conflict has already been resolved or rejected.
```

## Runtime boundary

Runtime sees canonical recipes only.

Runtime may consume:

- scene/elements;
- nodes/stages;
- scopes;
- values/signals;
- phases/triggers;
- diagnostics emitted by compiled execution.

Runtime must not consume:

- template definitions;
- mixin definitions;
- preset/profile layering instructions;
- slot declarations;
- override declarations;
- inheritance pointers.

If runtime behavior changes based on template ancestry, the design has failed.

## Schema and reference implications

D2 adds no Rust schema roots.

Future implementation phases should produce separate schemas for:

```text
source authoring documents:
    template
    mixin
    preset
    profile
    source recipe

expanded canonical contract:
    canonical recipe
    expansion report / provenance report
```

The source authoring schemas may contain template references and composition operations. The canonical recipe schema must not.

## Implementation-phase recommendations

When D2 moves into implementation, start with validation and expansion tests before runtime integration.

Recommended first implementation proof:

1. Load one template with one required element slot.
2. Fill the slot from one recipe.
3. Apply one values-only preset.
4. Produce a canonical recipe with no template refs.
5. Emit a provenance report.
6. Reject one implicit id collision.
7. Reject one preset that tries to add structure.
8. Reject one sealed-field override.

Do not start by porting real effects.

## Open questions for later phases

1. What exact wire syntax should express `override`, `append`, `replace`, and future `remove` operations?
2. Should template ids use dot paths, slash paths, or structured arrays in canonical ids?
3. Should profiles apply before or after presets in every context, or can recipe authors choose order?
4. Should expansion reports be mandatory build artifacts or opt-in diagnostics?
5. How much provenance should be embedded in canonical recipes for debug builds, if any?
6. Which fields are sealed by default in first implementation?
7. Are ordered mixins enough, or do we eventually need explicit mixin dependency constraints?
8. How should template version ranges be represented?
9. How should template cycles be detected and reported?
10. What is the smallest canonical recipe schema that can support the first descriptor phase?

## Phase D2 lock summary

D2 locks these decisions:

- Template composition is compile-time authoring behavior.
- Runtime receives only canonical expanded strict v3.1 recipes.
- Templates define structure and slots.
- Mixins/traits are additive reusable fragments.
- Presets and profiles are values-only.
- Expansion is deterministic.
- Conflicts require explicit override syntax or fail.
- Some fields can be sealed/final.
- Id namespacing is required.
- Slot contracts must define kind, cardinality, namespace, and diagnostics.
- Diagnostics need both source and expanded paths.
- Canonical recipes contain no template refs, no inheritance, and no legacy aliases.
